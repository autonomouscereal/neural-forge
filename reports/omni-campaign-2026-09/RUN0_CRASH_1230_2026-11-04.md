# Run 0 crash loop at step 1230 (2026-11-04)

Side session for the Chimera Omni lead. Cyril, 11-04: "[Cyril quote withheld]".

## Summary

- **What:** rank 0 (GPU1) died with SIGSEGV in `libcuda.so.580.178.04` (offset 33d045) five times during step 1230: 04:10, 06:28, 08:37, 10:54 and 13:10Z (kernel log times).
  - Each time, the supervisor resumed from step-00001200 and replayed steps 1201-1229, about 9 hours lost.
  - No monitor flagged it.
- **Root cause:** a cuFFT error-handling defect, triggered when the driver runs out of memory.
  1. The raw-audio loss calls `torch.stft`. cuFFT 10.9 (CUDA 11.8, the P40 venv) builds a plan for each new waveform shape.
  2. When a plan needs a kernel module that isn't loaded yet, cuFFT calls `cuModuleLoadData`.
  3. Rank 0 runs at ~23.1 of 24.4 GB, and CUDA loads kernels lazily. At the peak the driver had no memory left for that load, so it failed.
  4. cuFFT ignored the failure and passed the uninitialised module handle to `cuModuleGetFunction`. The driver dereferenced it and segfaulted.
- **Fix:** on the card, the audio loss now takes |STFT|^2 from a windowed-DFT matrix product, so training never builds a cuFFT plan.
  - The trainer preloads the product's kernels at start, while the card has room.
  - It treats a driver-side "CUDA error: out of memory" as an OOM (the step is skipped, not crashed).
  - It turns on faulthandler in the ranks.
- **Monitors:**
  - The supervisor stops at the second crash from the same checkpoint or step.
  - The autopilot and the lane watchdog alert on step rewinds and on stale checkpoints.
  - STATUS.md shows the checkpoint's age next to the step.

## Evidence

### The core dump

apport kept only the first crash: `/var/crash/_usr_bin_python3.12.1000.crash` (pid 105910, 04:10Z). It was unpacked to `/mnt/lexar/omni-campaign/run0/crash1230/unpacked/` and read with gdb.

- **Main thread:** `THPVariable_stft` -> `at::native::stft` -> `_fft_r2c_cufft` -> `CuFFTConfig` -> `cufftXtMakePlanMany` -> (libcufft.so.10 internals) -> `cuModuleGetFunction` -> SIGSEGV.
- **The other 131 threads** were idle, waiting on futexes.
- **The faulting instruction** is `mov (%rbx),%r12d` with `rbx = 0xa0a`, the CUmodule argument. The driver's message string at that site reads "CUmodule cannot be NULL".
- **In the cuFFT frame:**
  - The function-pointer slots resolve to `cuModuleLoadData` (…5e38) and then `cuModuleGetFunction` (…5e28).
  - The module-handle stack slot `-0x50(%rbp)` holds `0x0000000000000a0a`, not a pointer: the load did not write it.
  - The kernel log shows `segfault at a0a` for this crash and `segfault at 506` for the other four. A different garbage value each time is consistent with an uninitialised stack slot.
- **The other ranks** were in the `reducer.any(oom is not None)` all-reduce after their own micro-steps, so rank 0 died inside its forward/backward.
- **Timing:** 04:10:12Z is about 135 s after step 1229 ended, which places the crash in the generation pass of micro-step 2. Micro-step 3 of step 1230 has no generation chunk.

### Reproduction on GPU1

All runs used lanes.py claim-run with lane L-TRAIN on GPU1. Scripts and logs are in `/home/cereal/omni-campaign/run0/crash1230/`.

1. **Phase A (CPU, nice 19):** rebuilt rank 0's micro-batches for steps 1201-1232 exactly as a resume from step-00001200 builds them.
   - Same holdout draw first, the same data state, and the trainer's manifest precedence: v32 adopted over the checkpoint's v28.
   - Recorded every generation chunk's flow-loss inputs after the same seeded flow schedule: 193 chunks.
   - `shapes_1201_1232.pt`, `items_1201_1232.jsonl`.
2. **Phase B (GPU1):** replayed `_flow_objective` forward and backward on those chunks with a random x0 prediction (no model), so only the loss's cuFFT sequence ran: 5,016 `torch.stft` calls and 1,544 plans by step 1232.

| replay | driver memory | result |
|---|---|---|
| plain | ~21 GB free | survived (no eviction; the plan cache never reached 4,096) |
| card filled through PyTorch's allocator, 22.8-23.9 GB | allocator full | clean `torch.cuda.OutOfMemoryError` (the trainer skips the step) |
| warm 1201-1229, then the driver starved at 1230 | 2 MiB free, 0 allocator retries | survived: every module 1230 needs was already loaded |
| **starved from 1201 (non-FFT kernels warmed first)** | 2 MiB free | **first cuFFT plan: `CUDA error: an illegal memory access`** |
| **same, with the DFT spectrum** | 2 MiB free | **all 193 chunks survived, 0 cuFFT calls, 0 retries, 0 OOMs** |

How the starvation was done: PyTorch keeps a cached pool, large and small, big enough for every allocation, while raw `cuMemAlloc` takes every other byte. So only the driver's own needs find no memory, which is the state of rank 0 at its peak.

Single-plan probes (`stft_oom_probe.py`) showed the mechanism directly:
- With the driver starved, a never-loaded kernel fails to load: `torch.randn` gave "CUDA error: out of memory".
- With one plan per FFT size loaded first, new plan shapes succeed at 2 MiB free.

The live crash needed a cuFFT module load at a moment rank 0's driver had no room. The batch decides only which shape asked for it, and when. A starved cuFFT plan gives a segfault when the garbage handle is unmapped (the live case: 0xa0a, 0x506) and an illegal memory access when it happens to look valid (the replay).

### Ruled out

- **The data as such:** steps 1201-1229 replay token-identically, and step 1230's batch has nothing a fresh, roomy process can't run.
- **b06d417** (text masking), **the SDPA long-row option** (no FFT), **the 8k long lane** (odd steps; step 1230 has none) and **the v32 sources:** none of them touch cuFFT. Their only role is how full rank 0's card gets: peak 23.1 GB since the 8k lane.
- **Hardware:** no Xid or NVRM lines, and no retired pages pending on GPUs 1, 2, 3 and 5.
- **cuFFT plan-cache eviction:** about 20,000 plans past the 4,096 cap ran clean. Plain memory pressure through the allocator gives clean OOMs.
